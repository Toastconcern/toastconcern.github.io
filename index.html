ADB

Put an app already on your headset back onto an older build. This drives the adb already on your machine, through node tools/adb-bridge.mjs — so the headset trusts it already and there is no second debugging prompt. Plug in over USB and press Connect, or give an address to reach one over the network.

Connect over wireless instead

Wireless ADB is the same adb, reached over your network rather than a cable. Pair once with the six digits the headset shows, and it remembers this computer from then on — no cable at any point.

Pair — once per computer

  1. Developer Mode has to be on for the headset — a switch in the Meta Horizon phone app, under the headset's own settings.
  2. In the headset, turn on Wireless debugging, then choose Pair device with pairing code. It shows an address with a port, and six digits.
  3. Put both in here and press Pair, while that dialog is still open on the headset — it stops listening the moment it closes, and the port changes every time it is reopened.

Connect — every time after that

  1. Back on the Wireless debugging screen, read the address under IP address & Port. It is not the port you paired on.
  2. Put it here and press Connect wirelessly. Both ends have to be on the same network.

The connect port changes when wireless debugging is turned off and on again, but the pairing holds.

Get the app

MetaDB for Quest is this site as an app on your headset. It opens on Downgrade: every app installed, every build of each one, and an Install, Update or Downgrade on each. It keeps a copy of anything it downloads, backs up the version you are on, signs in through Meta's own login, and needs no relay. It is open source, and not on the store.

On the headset

Install from the Quest browser

  1. Open metadb.toastconcern.dev in the Quest Browser, come to this screen, and press Download MetaDB.apk below.
  2. Open the Files app and go to your downloads.
  3. On MetaDB.apk, press the ⋯ menu, then Open with → Package installer, and choose Install.
  4. MetaDB is in your library, under Unknown sources.

Browser · Chrome & Edge

Sign-in extension

On a computer, the extension signs this site in with your Meta account: press Sign in with Meta in Settings and both tokens are filled in from your Meta login. It reads Meta's two login cookies and hands them to this site only, when the site asks. Nothing is sent anywhere else. It is open source, and not in the extension stores yet, so it is added by hand:

  1. Download MetaDB-extension.zip and unzip it.
  2. Open chrome://extensions (or edge://extensions) and turn on Developer mode.
  3. Press Load unpacked and choose the unzipped folder.
  4. Come back to Settings and press Sign in with Meta. If you are not logged in to Meta in this browser, Meta's login opens in a new tab, and Settings fills in once you finish.

What this is

The oc_ac_at cookie. To get yours: sign in at secure.oculus.com, open your browser's developer tools, and under Application → Storage → Cookies copy its value. This is the one downloads authenticate with. Without it, the Download buttons in a build history have nothing to sign with and will point back here instead.

What this is

The oc_www_at cookie, from the same place. Everything that is not a download uses this one — store search, package lookups and your entitlements all need a token belonging to a logged-in account.

Leave it empty to fall back to the built-in public token, which can read public LIVE builds and nothing else. Treat your own token like a password — it signs in as you.

Inside an app

What each opened app shows and offers.

What this does

The link out to the app's page on meta.com, in each expanded app. On by default.

What this does

Adds a button to each expanded app that fetches its binary manifest — package name, download size, target SDK, required OS version, permissions and hashes. This is the query a headset runs to work out what to install, so it needs a logged-in account token. Genres, rating and age rating are not here — Check this app brings those in with the build history.

What this does

A build history is mostly internal builds that were never put on a channel. Normally only the released ones get a Download button; switch this on to get one on the rest too, shown in red so the difference is obvious. Whether the store hands any particular one over is its call — expect these to fail more often than not, even on an app you own.

What this does

Some apps ship a second file next to the APK — an OBB holding the assets — and it is no use having one without the other, so this is on to begin with: builds that have one get an OBB link beside the download. The store only reports OBBs from its release-channel query, which costs one extra request per channel on every check — switch it off if you would rather not spend them.

Developer

Request logging, and the relay the browser routes store requests through.

What this does

Off by default. With it on, every store request shows up in the box below — no developer tools needed, so it works on a phone too. Each line is the status and time that came back and the endpoint it went to. The access token is stripped from the logged URL, the same way the relay keeps it out of its own output, since it signs in as you.

Request log
What this is

Required for checks to work from a browser. The store replies with Access-Control-Allow-Origin: https://facebook.com, so this page is refused the response no matter which token is used — that is decided by the page's address, not the token. This is why the same request succeeds in Insomnia or curl, which are not browsers. A relay is a small service you control that fetches the URL and passes it back. Put {url} where the target should go, or leave it off and it will be appended.
